What I watch after a deploy

A small Datadog query, a personal alert and a link back to the exact window can answer a question raised by a change.

Mohamed Halawa/22 Nov 2026

A change has shipped. You want to know whether the service it touched is behaving differently. You can leave a Datadog tab open and remember to refresh it, but by the next pull request you may have forgotten which window you were watching.

I built on-my-watch to keep that question next to the code. It runs scheduled Datadog queries and puts the ones that cross a line in a Claude Code pane. Notifications go to the person who configured the query. A team monitor has a separate job, with an owner and an agreed response when it pages someone.

Start with one question

The project documentation uses a checkout service as an example. Its query counts production error logs for the checkout API.

service:checkout-api env:production status:error

The example uses a threshold of more than 20 errors in the configured window. That number illustrates the configuration. Picking a threshold for a real service requires knowing its ordinary traffic. Twenty errors in five minutes and twenty in an hour answer different questions. The pane compares recent runs of the same window size so that changing the window doesn’t distort the little chart beside the query.

Keep the window attached

When a value crosses the threshold, its row links to the Datadog query pinned to the time window that produced it. I can open the link later and still inspect the errors that triggered the notification. History keeps previous runs, so I can also return to the one before it. A crossing gives me a place to look. Establishing whether a deployment caused the errors takes the logs and the timing of the change.

The query can stay personal while I learn whether it’s worth keeping. If it repeatedly picks up a failure that someone should act on, it belongs in a team monitor with an owner. If the question was specific to one rollout, I can remove the query when that work is done.
